## 已关闭项

### 1. M4统一集成启动入口与启动顺序

- 启动入口：`ros2 launch ai_robot_bringup m4_bringup.launch.py mode:=sim|real`。
- `mode:=sim`按“公共安全/诊断层 → 仿真底盘与传感器实现 → 实体创建后加载控制器”的契约启动完整M4场景。
- `mode:=real`只启动公共安全、里程计契约和诊断节点；实体驱动尚未准入，因此保持无硬件输出的安全状态。
- 非法`mode`由launch参数`choices=['sim', 'real']`拒绝。
- 自动证据：`m4_launch_contract_test`检查模式、仿真实现选择和声明顺序；`test_bringup_launch.py`运行验证实体模式的安全节点、参数与诊断契约。

### 2. 底盘、编码器、里程计与TF集成

- 自动场景：`test_m4_motion_launch.py`通过M4统一入口启动完整仿真，不绕过`/cmd_vel`安全入口。
- 控制器：`joint_state_broadcaster`和`base_controller`均达到`active`状态。
- 接口与TF：持续收到`/joint_states`和`/odom`；验证`odom -> base_link -> sensor_link`链路存在。
- 方向与累计量：正向命令使左右轮累计量和里程计X正向增长，反向命令使三者反向变化。
- 一致性：以轮半径0.075 m换算的双轮平均位移与里程计位移绝对误差不超过0.04 m。
- 实测结果：M4运动集成launch测试1项通过，耗时13.94秒。

### 3. 编码器里程计与IMU融合

- 融合节点：`robot_localization/ekf_node`，二维模式，目标输出频率30 Hz，统一使用Gazebo桥接的`/clock`。
- 输入契约：轮式里程计重命名为`/wheel/odom`；IMU保持公共`/imu/data`。融合字段和过程噪声矩阵固化于`config/ekf_m4.yaml`。
- 输出契约：融合结果固定为`/odom`，类型`nav_msgs/msg/Odometry`，Frame为`odom`，child Frame为`base_link`，位姿与速度协方差为非零值。
- TF所有权：M4控制器配置关闭`enable_odom_tf`，仅`ekf_filter_node`发布`odom -> base_link`；`robot_state_publisher`发布`base_link -> sensor_link`。
- 自动证据：M4运动集成测试同时接收原始与融合里程计，验证单一`/odom`发布者、融合协方差、正向运动以及与轮式累计距离误差不超过0.04 m。
- 实测结果：融合launch测试1项通过，耗时13.59秒。

### 4. 雷达、TF与固定障碍物

- 固定场景：`m2_test.sdf`中`lidar_target`为中心位于`(2.0, 0.0)`、尺寸`0.5 × 0.5 × 1.0 m`的静态长方体。
- 几何预期：`laser_link`相对`base_link`前移0.1 m，因此目标前表面理论距离约1.65 m，中心方位约0 rad。
- TF契约：自动验证`base_link -> sensor_link -> laser_link`连通，`/scan.header.frame_id`继续由M3接口测试冻结为`laser_link`。
- 距离断言：取20帧前方±0.35 rad扫描，多帧最近距离中位数必须处于`[1.55, 1.75] m`。
- 方位断言：最近点方位中位数绝对值小于0.05 rad；距离小于1.80 m的目标回波必须同时跨越`-0.10 rad`和`+0.10 rad`，确认目标位于正前方且具有预期角宽。
- 静态证据：`test_sim_config.py`冻结目标Pose与碰撞体尺寸；动态证据：`test_m4_motion_launch.py`中的雷达几何测试通过。
- 实测结果：包含雷达几何与运动融合的2项M4场景测试通过，耗时15.38秒。

### 5. 相机最小图像处理链

- 处理节点：`ai_robot_sensors/image_processor`，由M4仿真入口启动，不改变M3原始图像接口。
- 输入输出：订阅`/camera/image_raw`的`rgb8`图像，发布`/camera/image_mono`的`mono8`图像；使用BestEffort/Volatile传感器QoS。
- 内容契约：输出保持`320 × 240`、`camera_optical_link`和原始采样时间戳，步长固定320字节，数据长度固定76,800字节。
- 频率与延迟：目标15 Hz，自动验收范围10.5–19.5 Hz；同时间戳输入输出的P95端到端接收延迟必须小于100 ms。
- 算法与异常：使用整数加权`(77R + 150G + 29B) / 256`生成灰度；拒绝非`rgb8`、非法尺寸、步长或数据不足的输入。
- 诊断：发布`perception/camera_gray`状态，包含输出编码、实测频率和最大处理延迟，供后续故障传播场景复用。
- 自动证据：4项转换单元测试通过；包含相机、雷达及运动融合的3项M4场景测试通过，耗时15.77秒。

### 6. 时间同步、QoS、TF完整性与启动顺序

- 时间源：Gazebo `/clock`单向桥接到ROS 2；自动验证时钟非零并持续推进。
- 时间戳：对`/odom`、`/scan`、`/imu/data`、原始及灰度图像分别抽样，要求时间戳非零、单调不倒退、不超前时钟0.1秒且最新数据年龄小于0.5秒。
- QoS：融合里程计固定Reliable/Volatile；雷达、IMU、原始图像和灰度图像固定BestEffort/Volatile；每个公共接口只允许一个发布者。
- TF完整性：自动验证`odom -> base_link -> sensor_link`以及雷达、相机、IMU全部下游Frame连通。
- 启动顺序：静态契约测试确认控制器通过`OnProcessExit(target_action=spawn_robot)`门控，只在机器人实体创建进程结束后加载；`mode:=real`继续不启动仿真实现。
- 自动证据：7项启动静态契约测试通过；包含时间、QoS、TF、相机、雷达和运动融合的4项M4场景测试通过，耗时15.43秒。

### 7. 可恢复故障注入基线

- 注入节点：新增`ai_robot_sensors/fault_injector`，通过独立的`m4_fault_injection.launch.py`启动，仅用于仿真验收，不接入实体驱动。
- 运行控制：注入默认关闭并原样转发；通过`/fault_injector/enable`服务启用或关闭，支持在同一场景中验证正常、故障和恢复三个阶段。
- 传感器中断：`scan|imu + drop`丢弃输入，供传感器诊断验证数据陈旧。
- 时间与Frame：`scan|imu|odometry + zero_stamp|bad_frame`分别注入零时间戳和指定错误Frame。
- 融合输入异常：`imu|odometry + nonfinite_data`分别注入非有限角速度或协方差，供`robot_localization`异常场景使用。
- 命令异常：`twist + drop|nonfinite_data`分别模拟命令中断和非有限速度；注入器位于`/cmd_vel`上游，不绕过速度限制和0.5秒超时停车。
- 可观测性：`fault_injection/<message_type>`诊断包含启用状态、故障模式以及接收、注入和转发计数。
- 自动证据：7项故障变换单元测试和1项launch静态契约测试通过；操作与话题映射记录于`docs/testing/m4_fault_injection.md`。

### 8. 诊断传播、安全停车与恢复

- 独立场景：新增`test_m4_fault_safety_launch.py`，使用合成20 Hz输入验证故障链，不依赖Gazebo负载，也不启动任何实体驱动。
- Frame诊断：雷达源Frame正常时`sensors/fault_lidar`为OK；注入`invalid_laser_frame`后为ERROR且`frame_valid=false`；关闭注入后恢复OK。
- 诊断盲点修复：`sensor_adapter`新增显式`validate_input_frame`开关；默认保持Gazebo Frame规范化兼容性，故障验收链启用后先验证上游原始Frame，避免错误Frame被覆盖后误报正常。
- 限速：向故障注入器上游持续发送1.0 m/s，安全节点输出固定限制为0.3 m/s，并发布`command limited` WARN。
- 超时停车：启用命令丢弃后仍持续发送上游命令，安全节点在0.5秒超时后发布零速度及`command timeout; stop sent` WARN。
- 恢复：关闭命令故障后无需重启，0.2 m/s命令恢复透传，安全诊断回到`command accepted` OK；故障注入诊断同步由WARN恢复OK。
- 自动证据：故障诊断与安全launch集成测试1项通过，最终复测耗时6.90秒；关闭提交为`0c83a57`。
